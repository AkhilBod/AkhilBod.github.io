My movie search app wasn't using its own vector index

Oct 2026 · Python, Postgres · github.com/AkhilBod/Seek

Back in June I built Seek, a search box for the Netflix catalog where you describe what you're in the mood for instead of typing a title. The example on the landing page is "dark funny revenge movie." I came back to it recently, typed that exact query, and got a wall of horror movies about revenge. Nothing funny anywhere on the page.

My first guess was that the embeddings were bad. They weren't. When I actually read the retrieval code, it turned out the app had never used its vector index to find anything. It grabbed up to 600 titles whose text contained one of the words in your query, sorted those by release year, and only then compared embeddings, in Python, on whatever came back. If a movie matched what you meant but didn't share a word with what you typed, it was never even in the running. There wasn't a vector index on the table at all. I had written "pgvector" in the README and believed it.

Before changing anything I wanted a way to tell whether a change was actually better, because "the results look better to me" is how I ended up here in the first place. Mood queries don't have one right answer, so I tested something that does. I picked 300 titles at random and had a language model write the kind of half-remembered query a person types when they can't think of the name, like "anime about high school basketball and unrequited love." Then I checked where each version of the search ranked the title the query came from.

The model needed babysitting. A lot of its first attempts slipped in a character's name or a word from the title, which would make the test trivially easy, so I filtered out any query that contained either. That threw away 96 of them. I'm glad I checked before trusting the batch.

The old pipeline put the right title in the top 10 only 20% of the time. Searching the vector index directly, with nothing else, got 73%, and it was about seven times faster because the database was doing the work instead of Python.

VersionRight title in top 10Exact-title search, right title firstMedian retrieval
Old pipeline20%58%412 ms
Keywords only11%80%12 ms
Vectors only73%83%62 ms
Vectors + keywords, equal weight63%89%72 ms
Vectors + a little keyword (shipped)73%88%76 ms

The part I got wrong was the obvious next step. Everything I'd read says hybrid search, combining vector results with keyword results, beats either one alone, so I expected that to be the winner. On the vague queries it was worse than vectors alone. Words like "love" and "family" show up in thousands of synopses, and giving those matches equal say dragged the right answer down the list.

Keywords aren't useless, though. When I reran the test with people typing the exact title instead, keyword matching fixed a bunch of cases the vectors fumbled, mostly short or unusual titles. So the version I shipped mostly listens to the vectors and gives keyword matches a tenth of the weight. That keeps nearly all the gain on vague queries and gets the right title first 88% of the time when you type its name. I also dropped the hand-tuned scoring formula that used to sit on top, because the benchmark showed it was pushing good results down.

There's a catch in my own test that I should be upfront about. The fake queries were written from the same synopses the embeddings were built from, which gives vectors a home-field advantage, and "dark funny revenge movie" still doesn't have a score. The fix for that is real queries from real people, which is the next thing I want to collect. The code, the benchmark, and both result tables are on GitHub if you want to rerun it.
