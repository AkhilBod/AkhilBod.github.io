Never charge someone for a failed AI call

Oct 2026 · InterviewSense · PostgreSQL

InterviewSense runs on daily credits. Each AI feature costs a few, and they reset every day. That sounds like a counter you subtract from. It isn't.

The naive version goes like this. A request comes in, you subtract a credit, then you call the model. If the model call fails, times out, or the user closes the tab halfway through a streamed answer, the credit is already gone. People are forgiving about a slow answer. They are not forgiving about paying for nothing.

Reserve, then commit

The fix was to stop treating a credit as spent the moment a request starts. For most web features that just means charging after the model call succeeds. The desktop app streams answers live, though, and you need to know there's a credit before you start. So there, a request reserves a credit first. The reservation is its own row with a status and an expiry. When the response finishes cleanly, the reservation is committed. If anything fails, it gets refunded.

The subtraction itself is one conditional update:

UPDATE "User"
SET "dailyCredits" = "dailyCredits" - 1
WHERE "id" = $1 AND "dailyCredits" >= 1

If that touches zero rows, the user is out of credits and we return a 402 before the model is ever called. Because the check and the decrement are one statement, two requests racing each other can't both read "1 credit left" and both spend it. The reservation row is created in the same serializable transaction, so you never get a decrement without a record of why it happened.

What happens when nobody says anything

The annoying failure isn't an error. It's silence. A desktop client loses its network connection mid-stream and never tells the server the response finished. The reservation just sits there, holding the credit.

So every reservation expires after 10 minutes. Before reserving a new credit, the server sweeps that user's expired reservations and refunds them. Each refund flips the status from reserved to refunded with a conditional update, and only counts if it actually changed a row. That way two sweeps running at once can't refund the same reservation twice. The refund is capped at the user's daily limit, so a late refund after a daily reset can't push someone above their allowance.

The takeaway

Write the failure paths first. The happy path for billing is maybe ten lines of code. Everything that makes it correct lives in the cases where the network dies, the model times out, or two tabs hit the same endpoint at once. None of those show up in a demo.
