Two writers, one table, no locks

Oct 2026 · Python · github.com/AkhilBod/tinylake

Two updates hit the same cluster at almost the same moment, and one of them quietly erased the other. No error. No crash. A customer's settings were just gone.

That was the bug I spent the most time on during my internship at Nutanix. The fix itself wasn't huge, but getting there meant thinking hard about one question: what should happen when two people change the same thing at once?

The question stuck around after the summer ended. A year earlier I'd built a backtester for a hackathon on top of Delta tables, which are just Parquet files in a folder. Parquet files can't be edited after they're written. And yet lots of jobs write to those tables at once, and nobody ever loses data. I'd relied on that the whole hackathon without once wondering how it worked. So I built a small version to find out.

The table is a diary

The trick took me embarrassingly long to see. Next to the data there's a folder of numbered notes. Note 0 says what columns the table has. Note 1 says "these three files are in." Note 2 says "add this file, drop that one." The table is whatever you get from reading the notes in order.

Nobody edits a note or a data file, ever. You only add new ones. Once I got that, a feature I assumed would be hard came for free. Want the table as it looked last Tuesday? Stop reading at Tuesday's note.

Back to my bug

Here's the Nutanix problem in this world. Two writers finish at the same time and both try to write note 13. The filesystem lets exactly one of them create the file. The loser has to figure out whether its change still makes sense on top of the winner's.

The whole commit boils down to a loop like this:

version = read_version + 1
while not create_if_missing(f"_log/{version}.json", my_changes):
    check_winner(version)  # raises if their change breaks mine
    version += 1

Most of the time the answer is "go ahead." If the winner only added data, the loser takes note 14 and carries on, with no redone work. It only backs off when the winner deleted a file the loser was relying on. That's basically my summer bug, solved by checking what changed before writing instead of after. Seeing it pop up in a totally different system was my favorite part of the project.

I didn't trust it until I tried to break it. I had 8 separate processes hammer the same table with 120 commits at once, then counted every row. All there, none doubled. The sneakier cases got their own tests. One example: if a delete loses a race to a new append, the new rows survive the delete. That sounds like a bug, but the real thing does it on purpose. I wanted it written down before it confused me later.

The guess I got wrong

Every file also remembers its smallest and largest value per column, so a search can skip files that can't contain a match. How much gets skipped depends on how the rows are laid out, and I was confident I knew the best layout.

There's a trick called Z-order that weaves two columns together, and it's supposed to shine when you filter on both. I benchmarked it on 2 million rows fully expecting it to win. It tied. Plain sorting had already cut the search to 3 files out of 200, and there was nothing left to beat. Z-order's real strength turned out to be the case I hadn't planned for: you don't know which column the next search will use. Sorting only helps one column, while Z-order kept both of them cheap.

I like that result more than if I'd been right. I would have bet on the wrong layout, and now I know to measure first.

What's next

Deleting a single row still rewrites the whole file it lives in, which bugs me. The fix is a small side file that marks dead rows, so that's the next thing I want to build.

The code is on GitHub. The README has the full benchmark if you want the numbers.
