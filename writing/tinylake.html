The bug that sent me building a tiny data lake

Oct 2026 · Python · github.com/AkhilBod/tinylake

Most of what I remember from my Nutanix internship comes back to one bug. When two partial updates to the same cluster came in close together, one could overwrite the other, and whatever the first had changed was lost. A customer would set something and later find it had quietly reverted. I spent a lot of the summer in that code, reworking how partial updates got applied so that concurrent ones would stop clobbering each other.

What bugged me afterwards was that I'd already used a system that deals with this exact situation and never given it a thought. The year before, at a hackathon at Federated Hermes, my backtester read and wrote Delta tables on Databricks. A Delta table is a folder of Parquet files, and you can't open a Parquet file and change a row in it. People still point a pile of jobs at the same table and it holds up fine. I wanted to know how, and reading about it only got me so far, so I tried writing a small version myself. It came out to about 800 lines of Python, and I called it tinylake.

The piece that made everything else make sense was the log. Next to the data files sits a folder of numbered JSON files, one per commit, and each one lists which data files to add and which to remove. To find out what's in the table, you start at commit zero and replay them in order. Since nothing is ever changed in place, you can also see the table as it was at any earlier point by stopping the replay early. Delta calls that time travel, and I'd assumed it would be a big chunk of work. It ended up being one optional argument.

Concurrency is where my Nutanix bug shows up again. Say two writers both start from commit 12, do their work, and both try to save commit 13. All the storage has to promise is that creating a file fails if the file is already there, so exactly one of them gets 13. The other reads what the winner did and decides whether its own change still holds up. If the winner only appended rows, the loser just tries again as commit 14, and because its data files are already written, nothing gets redone. If the winner deleted a file the loser had read from, the loser gives up and raises an error instead of writing over it. That second case is basically the fix I wrote over the summer, sitting in a completely different system, and I'll admit it was satisfying to find it there.

Stripped down, a commit looks like this:

version = read_version + 1
while not create_if_missing(f"_log/{version}.json", my_changes):
    check_winner(version)  # raises if their change breaks mine
    version += 1

I didn't want to take it on faith, so I had eight processes append to one table at the same time, 120 commits between them, and then counted the rows to make sure each one landed exactly once. I also wrote a test for a case that looks wrong the first time you see it: if a delete races an append and loses, the newly appended rows survive the delete. Delta works the same way on purpose, but I'm pretty sure I'd have filed it as a bug six months from now if I hadn't pinned it down.

The other thing I wanted to understand was why people bother reorganizing their files at all. Every entry in the log records the min and max of each column for that file, so a query can skip any file whose range can't possibly match. How much that helps depends on how the rows are spread out. I generated 2 million rows with two random columns and tried three layouts: the order the rows arrived in, sorted by the first column, and Z-ordered on both, which interleaves the bits of the two columns so rows with nearby values end up in the same files.

I went in expecting Z-order to win clearly on queries that filter both columns, since that's the case it's designed for. It tied with plain sorting, because sorting had already narrowed those queries to 3 files out of 200 and there wasn't anything left to gain. Where Z-order earned its keep was on queries that only filtered the second column. The sorted table had to read all 200 files for those, while the Z-ordered one read about 21. So sorting wins when you know what people will filter on, and Z-order is the safer bet when you don't. The full numbers are in the README.

The obvious gap right now is deletes. Removing one row means rewriting the whole file it lives in, which is fine for a toy and pretty bad for anything real. Delta gets around it with deletion vectors, small side files that mark which rows are gone, and that's what I'd like to add next. The code is on GitHub if you want to dig through it.
