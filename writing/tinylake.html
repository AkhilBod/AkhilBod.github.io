How a lakehouse table works, built small

Oct 2026 · Python · github.com/AkhilBod/tinylake

Formats like Delta Lake turn a folder of Parquet files into something that behaves like a database table. You get transactions, several writers at once, and the ability to read the table as it was last Tuesday. I had used that from the outside but couldn't have explained how a pile of immutable files pulls it off. So I built a small version, about 840 lines of Python including tests, to find out.

The short answer is that almost everything comes from one idea: the table isn't the files, it's a log of which files count.

The log is the table

A table is a directory of Parquet files plus a _log/ folder. Each commit is one numbered JSON file, and each line in it is an action: this file was added (with its row count and the min and max of every column), this file was removed, the schema is now this. To find out what version 12 of the table contains, replay commits 0 through 12 and see which files are left.

Data files are never edited. A delete reads the files that hold matching rows, writes new files without those rows, and commits "remove the old ones, add the new ones" as one action list. That one choice gives you a lot for free. A reader that loaded version 11 keeps reading version 11's files, no matter what writers do. Time travel is just replaying fewer commits. Undoing a bad write would be a commit that puts the old files back.

Replaying from zero gets slow on a long-lived table, so every 10 commits a writer also saves a checkpoint, which is the full list of live files at that point. Loading a snapshot then means reading one checkpoint and at most nine commits. The checkpoint is purely a cache, and one of the tests deletes the checkpoints and checks that a full replay gives exactly the same file list.

One storage primitive

For this to be a transaction, two writers must never both create commit number 13. The only thing the log needs from storage is "create this file only if it doesn't exist yet." Object stores offer that as a conditional PUT. On a local disk I write the commit to a temp file and then os.link() it into place, which fails if the name is taken. A reader can never see a half-written commit, because the file only appears once it's complete.

Writers that don't lock

Nothing is locked while a writer works. A transaction reads the latest version, writes all its new Parquet files, and only then tries to create the next commit. If someone else got there first, it reads their commit and asks whether its own change still makes sense on top:

  • If the other writer changed the schema, stop.
  • If the other writer removed a file this transaction read or meant to remove, stop. That's two deletes hitting the same rows, or a delete racing a compaction that rewrote the files it was working from.
  • If the other writer only added files, there's no problem. Try the next commit number. Nothing gets redone, because the new Parquet files are already written.

That last rule is why appends scale. Two appends never conflict, so the loser just takes the next number. The test I trust most starts 8 separate processes making 120 commits between them, then checks that the table ends at version 120 with every row present exactly once.

These rules are a simplified version of Delta's WriteSerializable isolation, and they have a consequence worth knowing. If a delete loses a race to an append, the delete is ordered after it and doesn't see the appended rows, so those rows survive the delete. There's a test that pins that down, because it's exactly the kind of behavior that surprises someone later.

Skipping files you don't need

Since every add action stores per-column min and max, a query can throw files away before opening them. If a file's x values run from 400,000 to 410,000, a query for x < 100,000 never reads it. Whether that helps depends entirely on how rows are laid out across files, which is what the benchmark measures.

It writes 2 million rows with random x and y into 200 files, then rewrites the table twice: once sorted by x, once in Z-order on (x, y). Z-order interleaves the bits of both columns, so rows that are close in both end up near each other. Thanks to time travel, all three layouts stay readable from the same table, so the same 50 random queries run against each. Each query's range covers 1% of the column.

In arrival order, every file covers nearly the whole range of every column, so stats skip nothing and every query reads all 200 files. Sorting by x is perfect for queries on x, about 25 times faster, and useless for queries on y. Z-order gives up part of the x win (31 files instead of 3) to make y queries 10 times cheaper too.

The result I didn't expect was the last column. I assumed Z-order would win clearly when filtering on both columns, and it didn't. A 1% range on x alone already narrows a sorted table to 3 files, so there was nothing left to win. Z-order earns its keep when you don't know which column the next query will filter on, or when each filter on its own is too wide to prune much.

What it leaves out

A lot. There's no partitioning, no schema evolution, no MERGE, and no deletion vectors, so a delete that touches one row still rewrites the whole file. Stats are only min and max. Everything lives on one local filesystem. The commit protocol only needs put-if-absent, which S3 now supports, but there's no object store backend.

The piece I'd add next is deletion vectors. Copy-on-write deletes are simple and correct, but rewriting a 100 MB file to drop one row is the obvious cost in this design, and marking deleted rows in a small side file is how Delta avoids it.

The code, tests, and benchmark are on GitHub. It needs only pyarrow and numpy, and pytest runs all 22 tests in a few seconds.
