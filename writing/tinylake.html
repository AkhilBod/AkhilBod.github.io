Two writers, one table, no locks

Oct 2026 · Python · github.com/AkhilBod/tinylake

This summer at Nutanix I spent a good chunk of time on one bug. Two partial updates to the same cluster could land at once, and one would quietly wipe out the other. Customer configs, just gone. I rewrote the update logic so concurrent writes stopped stepping on each other.

A year before that I'd won a hackathon at Federated Hermes with a backtester that ran on Databricks. The tables were Delta tables by default and I treated them like magic. I never once thought about what happens when two jobs write to one.

After Nutanix I started wondering. Delta tables are just Parquet files in a folder, and Parquet files can't be edited. So where do the transactions come from? I built a tiny version to find out. It's about 840 lines of Python with the tests.

A folder and a diary

The whole thing hangs off a _log/ folder that sits next to the data. Every commit is one numbered JSON file. Each line says something like "added this file, here's the min and max of every column" or "removed that file." To get version 12 you replay commits 0 through 12 and see which files survive.

Data files are never touched after they're written. A delete reads the files with matching rows, writes new copies without them, and commits "remove these, add those" in one go. The old files stick around, so reading last week's version means replaying fewer commits. I expected time travel to be a big feature. In the code it's an optional version argument.

Replaying from zero every time gets slow, so every 10th commit also saves a checkpoint with the full file list. Loading any version is then one checkpoint plus at most 9 commits. Checkpoints are only a cache, and one test deletes them all and makes sure the table comes back identical.

Who gets commit 13

Everything depends on one rule: two writers can't both create commit 13. Storage has to give you "create this file only if it doesn't exist." S3 does that with a conditional PUT. On my laptop I write the commit to a temp file and os.link() it into place, which fails if the name is taken. Readers also never see a half-written commit, because the file only shows up once it's complete.

The Nutanix bug, again

This is the part I actually came for. A writer reads the latest version, does all its work, and only then tries to grab the next commit number. If someone beat it there, it reads the winner's commit and decides whether it can still go:

  • Winner changed the schema: give up.
  • Winner removed a file this writer read or planned to remove: give up. Two deletes on the same rows, or a delete racing a compaction, end up here.
  • Winner only added files: no problem. Take the next number and go. The Parquet files are already on disk, so nothing gets redone.

The second rule is my config bug in a different costume. A writer working off stale data has to find out before it commits. Here it finds out by checking exactly which files the other writer removed. The third rule is why appends scale. Two appends never step on each other. One test starts 8 processes making 120 commits at once and checks that the table ends at version 120 with every row there exactly once.

Delta calls this WriteSerializable, and mine is a stripped-down copy. It has one side effect that surprised me. If a delete loses a race to an append, the delete lands after it in the log but never saw the new rows, so they survive the delete. Delta works the same way on purpose. I wrote a test for it so future me doesn't file it as a bug.

Reading less

Since every file records min and max per column, a query can throw files away without opening them. A file whose x runs from 400,000 to 410,000 can't match x < 100,000. How much that buys you depends on how rows are spread across files, so I measured it.

I wrote 2 million rows with random x and y into 200 files, then rewrote them sorted by x, then Z-ordered on (x, y). Z-order interleaves the bits of both columns so rows that are close in both land in the same file. Time travel keeps all three layouts readable from one table, so the same 50 queries ran against each. Every range covers 1% of its column.

In arrival order every file holds a bit of everything, so the stats skip nothing. Sorting by x makes x queries 25x faster and does nothing for y. Z-order splits the difference: a lot worse than the sort on x, 10x better on y.

I got the last column wrong. I was sure Z-order would win big on queries that filter both columns, and it tied. A 1% range on x already narrows a sorted table to 3 files, so there was nothing left to take. Z-order pays off when you don't know which column the next query will filter on.

What I'd build next

There's no partitioning, no schema changes, no MERGE, and the only stats are min and max. It all lives on one disk.

Deletes bother me most. Dropping one row rewrites the entire file. Delta fixes that with deletion vectors, a small side file that marks which rows are dead, and that's next on my list.

Code and tests are on GitHub. It only needs pyarrow and numpy, and pytest runs all 22 tests in a couple of seconds.
